## Packaging and installation validation deferred by NO BUILD

The current source declares the expected assets and launchers, but a source manifest is not proof of wheel/sdist contents or installed file ownership. After the build restriction is lifted, an operator should:

1. Use a disposable copy of this exact tree and isolated HOME/XDG directories; record the source revision and working-tree diff.
2. Build wheel and sdist in that disposable copy; inspect both archives for every filesystem-loaded `picard/ui/dlmtags/icons/*.svg`, the DLMtags PNG/SVG resources, `dlmtags.desktop`, and only DLMtags launchers/icons. Reject upstream Picard desktop/icon paths.
3. Install upstream Picard and DLMtags into separate disposable Python prefixes. Inventory and hash both prefixes before and after installation, then launch both with one isolated HOME and verify separate settings, cache, IPC and desktop integration.
4. Test a **third disposable shared prefix** only after the `picard/` namespace collision is removed or an equivalent isolation mechanism exists. Compare installed file manifests and hashes before/after each install; require zero replacement of upstream Picard files. Do not run this experiment against a user's installation.

## Remaining closure risks

- Same-environment installation collision is a confirmed P0 blocker; current package contents and clean-install behavior are unverified under this audit's NO BUILD rule.
- Confirm Results lacks direct Year/Genre approval; the automatic matched path is broader than the four reviewed fields. P1 implementation is therefore partial even though the safer Find Tag/manual approval path works.
- No representative ground truth or comparative export set exists. Accuracy remains **NOT VERIFIED**, not a measured tie or win.
- The historical release audit also records undocumented provenance for new DLMtags art. No new rights evidence was found in the current tree; redistribution should wait for that separate release gate.
